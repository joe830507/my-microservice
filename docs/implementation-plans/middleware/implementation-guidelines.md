# 中介軟體實作共用規範

適用於階段 D、E，與各階段計畫的特殊要求一併閱讀。這裡集中原本兩份計畫重複的原則；階段專屬的依賴、migration、測試與計畫變更仍以該計畫為準。

## 流程與提交

1. 一次只做一個 Step；實作、測試、更新文件後單獨 commit，才開始下一步，不把整個階段交錯在一次提交。
2. 階段實作 commit 使用 `Phase D<N>: <英文簡述>` 或 `Phase E<N>: <英文簡述>`，本文說明重點並保留專案要求的 `Co-Authored-By` 行（須符合實際共同作者）；不使用 `fix(events):` 等 conventional commit 格式。
3. 只提交該步驟的檔案；`.vscode/launch.json` 是使用者本機設定，永遠不要提交。不自行 push、開 PR 或修改 `main`，由使用者決定。
4. 開始前讀路線圖、事件實作紀錄、事件契約及階段列出的參考文件與現有程式／測試風格。完成後在實作紀錄最後列出「最不確定、希望審查者重點看的地方」。

## 文件與證據

- 計畫寫要求與進度摘要，實作結果放對應的 `*-implementation-record.md`：標頭（日期、分支、對應、狀態）→ 內容表 → 規則 → 驗證結果 → 遇到的問題 → 已知限制 → 最不確定的地方。
- 文件與註解使用繁體中文（程式識別字、指令、設定鍵名除外）；文件與證據使用 UTF-8 無 BOM。Windows PowerShell 的 `>`、`Out-File` 預設可能產生 UTF-16；寫檔須明確指定 UTF-8 無 BOM，或使用 `Out-File -Encoding utf8` 後去掉 BOM。
- 驗證須可重現：附指令、時間與數字；未親自驗證標「待驗證」，不能寫成完成。部署證據放 `evidence/phase-d/` 或 `evidence/phase-e/`。
- 每一步同步計畫進度、路線圖狀態與文件索引；索引中一個檔案只列一次。新安全限制加入 [known-issues.md](../../security/known-issues.md)，沿用既有 SEC 編號，新增才接續編號。
- 做不到或沒做的列入已知限制／待驗證。無法自動化的項目須說明由誰、如何驗證；不能用「不驗收」略過。
- 計畫有錯或不合理，先停下來記錄，再依各計畫的「計畫變更紀錄」處理，不可默默偏離。

## 程式與資料庫

- 跟隨現有套件、命名、Lombok、Jakarta Validation 與 Spring 用法。註解寫原因與取捨，類別／方法上方用 `//`，不要翻譯程式碼；參考 `ProductServiceImpl`、`DownstreamCaller`、`OutboxRelay`，設定 record 參考 `StorageProperties`。
- 使用 `import`，不用 `java.util.Map.of(...)` 等全名；依現有順序整理，刪除未用的 import、參數與欄位。
- 設定使用 `@ConfigurationProperties` record，不散落 `@Value`。日誌使用 `@Slf4j`，不得記錄完整事件 payload 或使用者資料。
- 共用元件放 `common`，但不能含單一服務的業務名詞（如訂單錯誤碼、通知模板名稱）。
- 不加功能旗標同時保留新舊路徑；階段 C 的 `app.events.enabled` 已移除。不得在 listener 或請求執行緒用 `Thread.sleep` 重試，採各階段指定的退避方式。
- 不引入計畫未列的依賴；必要變更依階段規範記錄版本與理由。
- 已存在的 migration 絕對不改，以保留 Flyway checksum；需要變更就新增。SQL 須能在 PostgreSQL 18 執行，並記錄使用哪些 18 才有的功能。

## 測試與誠實回報

- 各步驟驗收與測試重點須有對應自動化測試，名稱能看出驗證目的。使用各階段指定的真實容器；故障用停容器或不可達位址模擬，不能 mock 成功路徑。
- 開發時跑修改的模組；D、E 實作 commit 前依各階段測試規範跑完整 reactor，記錄時間、耗時與模組數。測試須能在離線 Maven 與本機已有映像環境執行。
- 等待使用輪詢加逾時（已有 Awaitility 可沿用，否則用短輪詢工具），不要用 `Thread.sleep` 等時間；失敗訊息須指出等待目標。
- 測試各自準備與清理資料，不依賴順序。既有測試不能改弱；不得為了通過而放寬斷言、跳過測試或加 `@Disabled`。確實需要調整時，記錄理由與後續。
